## 4.1.7 — 24.11.2026 (синхронізатор 4.1.7; у репозиторії npa-redaktsii)

Причина: звірка картки 2343-12 на zakon.rada.gov.ua 24.11.2026 — 18.01.2013 набрали чинності дві редакції:
«Нова редакція, підстава - 4212-VI» (сторінка `ed201301186`) і «Редакція, підстава - 5405-VI, 5410-VI, 5518-VI»
(`ed20130118`). В архіві текст `20130118` — пізніша редакція, але підпис — від першої; тексту 4212-VI не було.
API JSON також змішує ці два рядки (опис від першого, підстави від другого).

- **Окрема редакція того самого дня.** Ідентифікатор порталу з 9–10 цифр (перші 8 — дата) зберігається як є
  (`red/201301186.txt`, посилання `/ed201301186` працює на сайті). Записується лише командою
  `anomaly --record-separate --order before|after [--opys … --pidstava …]` за умов: HTTP 200, текст (не HTML),
  DocumentDate = перші 8 цифр, контрольний `ed<дата>` отримано, тексти різні (однакові → дублікат, `--record`).
  Порядок у межах дня — поле `poriadok_u_dni` (задає власник за карткою сайту); доказ — `api.separate_edition_ids`;
  під час sync вирішений ідентифікатор враховується в повноті каталогу.
- **Сортування редакцій** — за датою, порядком у межах дня, ідентифікатором (`edition_sort_key`), а не рядком `ed`
  (інакше `201301186` стала б після `20130118` і вважалася б чинною на 18.01.2013).
- **`edition_date()`**: перевірка DocumentDate, класифікація текстів (verify) і вибір чинної редакції (`chynna`)
  для 9–10-значних ідентифікаторів беруть дату з перших 8 цифр.
- **Команда `pravka`** (без мережі): ручне виправлення опису й підстави редакції; поле `ruchna_pravka`
  (з попереднім значенням і причиною) має перевагу над API і старою карткою під час наступних sync. Тіло тексту не
  змінюється (SHA-256 чинний), у шапці — лише старий опис і рядок «# Підстава:».
- **`npa.py`**: на дату, коли набрали чинності кілька редакцій, — попередження з переліком і вказівкою, що застосовано
  останню за карткою сайту; у `redaktsii` окрема редакція позначена `[ed<ідентифікатор>]`.
- Тести: +19 (`tests/test_v4_1_7_same_day.py`), разом 122. Жива перевірка — `tests/live/live_v417.py`, `run_v417.bat`
  (робоча копія лише з 2343-12, без повного архіву).

- **П. 2. `verify` без `--repair`:** ненульовий код, якщо є хоч один **очікуваний** відсутній, пошкоджений
  або з невірною датою текст (раніше — лише corrupt/date_mismatch). Відсутні поза очікуваним набором режиму
  (напр. історичні в chynna) не враховуються.
- **П. 3. `verify --repair`:** окремі лічильники «відновлено / не вдалося / пропущено / залишилося» і причина
  зупинки (бюджет, 403/429); код 0 лише якщо відновлено всі цілі. Умовні 3000xxxx без
  `--include-conditional` — «пропущено», не успіх.
- **П. 4. Змішаний `modified`:** будь-який нерозпізнаний modified у рядках акта змушує перевірити JSON-картку,
  навіть якщо інші значення розпізнано.
- **П. 5. `edcnt`:** каталог повний лише за `counted == edcnt` і без невирішених аномалій; `counted > edcnt` —
  розбіжність із причиною (скільки додано з doc-update). На живих даних 23.11.2026 у всіх 44 повних актах
  counted = edcnt, тож статус жодного з них не змінюється.
- **П. 6. `SKILL.md`:** однозначні правила дозволів — що Claude робить без дозволу, що лише за прямим дозволом,
  межі постійного дозволу власника (лише дані в npa-redaktsii); суперечливі рядки прибрано.
- **П. 7. `anomaly`:** недоступна контрольна редакція (404/302 чи інша помилка) або недоступний ed{raw}
  дає контрольований висновок `inconclusive` з причиною, без `duplicate_of` і без запису в картку.
- Тести: `tests/test_v4_1_1_regressions.py` (11); `tests/run_offline_tests.bat` — офлайн-тести на Windows.

## 4.1 — 23.11.2026 (кандидат)

Основа: `sync_api_v4.py` (SHA-256 3a74b05c710414b2b3a3b80bbdf9b57c13747c74ed59c2e6b0b62c99e1552bc8).
Повний diff від v4 — `v4_to_v4_1_5.diff` (включає 4.1.1–4.1.5).

### P0
- **Повнота історії (ТЗ розд. 2, 6).** Прибрано формулу `valid + invalid_eds + bulk_invalid >= edcnt`.
  Некоректні ідентифікатори зберігаються в `api.invalid_source_records` з походженням (`eds` / `doc-update`),
  причиною й nreg, дедуплікуються; невирішений ідентифікатор (`api.unresolved_edition_ids`) завжди блокує
  підтвердження. Нові поля: `edition_catalog_complete`, `history_reason`, `counts` (edcnt, коректні дати з JSON,
  додані з doc-update, datred, кількість аномалій), `texts` (verified / legacy / corrupt / date_mismatch /
  missing з очікуваних), `all_texts_verified`. `history_complete` (сумісне) = каталог повний ∧ режим povna ∧ не snapshot.
  Доказ дубліката — лише командою `anomaly … --record` (`api.resolved_edition_ids`).
- **modified у doc-update (розд. 3).** Розбирається окремо від HTTP Last-Modified файла; на акт — максимум;
  зберігається в `api.doc_update_modified`. `--changed` запитує картку, якщо modified змінився, базового значення
  ще немає (перший запуск) або формат нерозпізнаний; тексти при цьому не завантажуються повторно.
  Відсутність у doc-update більше не означає «вручну»: перевіряється JSON-картка.
- **status (розд. 4).** `resolve_status`: явний 0 очищає стан; відсутнє поле / null — попередній стан з
  попередженням; невідомий ID — порожній стан, сирий ID, попередження.
- **Цілісність текстів (розд. 5).** `classify_text_file` і команда `verify` (без змін файлів і мережі);
  `--repair` — лише явно, з перевіркою DocumentDate і атомарним записом; legacy — лише з `--include-legacy`.
  `sync` не позначає пошкоджений наявний текст як перевірений і не перезаписує його.
